# #1500 — Add support for the SCRAM-SHA-1, SCRAM-SHA-256 and SCRAM-SHA-512 SASL mechanisms

- Commit: b18832bf
- Verdict: MINOR

## What it changes
Adds client-side SASL SCRAM-SHA-1/256/512 support.

- New `src/irc/core/scram.c` / `scram.h`: a SCRAM state machine
  (`scram_session_create`, `scram_process`, `scram_session_free`) built on
  OpenSSL's EVP/HMAC/PBKDF2 primitives. It produces client-first /
  client-final messages, derives the client proof, and verifies the server
  signature.
- `sasl.h`: adds three new `SASL_MECHANISM_SCRAM_SHA_*` enum values (inserted
  before `SASL_MECHANISM_MAX`).
- `sasl.c`: `sasl_start` sends `AUTHENTICATE SCRAM-SHA-*`; new
  `SASL_MECHANISM_MAX` case emits a failure and finishes negotiation;
  `sasl_step_complete` drives the SCRAM handshake via a new helper
  `scram_authenticate`.
- `irc-servers.h`: adds `SCRAM_SESSION_REC *scram_session` to the connect
  record and `#include`s `scram.h`.
- `irc-core.c`: frees `scram_session` on connect teardown.
- `irc-servers.c`: initializes `server->sasl_success = FALSE` in
  `irc_server_init_connect`.
- `irc-servers-setup.c`: maps the `SCRAM-SHA-*` mechanism names from config,
  requiring username+password, and now sets `sasl_mechanism =
  SASL_MECHANISM_MAX` (sentinel) for unrecognized mechanisms instead of
  leaving it as the default PLAIN.
- ABI version bumped 52 -> 53 (correct, given the new struct field).
- meson: builds `scram.c`, installs `scram.h`. Help text updated.

## Release-safety findings

No crash/UB/memory-corruption or auth-bypass issue found. Buffer sizes are
consistent (`digest_size` matches the HMAC/PBKDF2 output for each SHA
variant; `stored_key[EVP_MAX_MD_SIZE]`), allocations are freed on all
success and error paths, the step machine is driven internally so a server
cannot jump to a later step with NULL `salted_password`/`auth_message`, and
malformed server messages return `SCRAM_ERROR` cleanly. The authentication
decision still rests on the `verifier == ServerSignature` `memcmp`, which is
intact. The following are real but non-blocking:

1. Username is not SCRAM-escaped (minor injection / interop, not remotely
   exploitable). `process_client_first` builds the message with
   `g_strdup_printf("n,,n=%s,r=%s", username, nonce)`. RFC 5802 requires the
   `n=` value to have `,` -> `=2C` and `=` -> `=3D` escaped (and SASLprep
   normalization). A username containing `,` or `=` will corrupt the
   client-first-message (e.g. a `,` injects extra SCRAM attributes),
   breaking auth. The value comes from the user's own config, not from the
   network, so this is a correctness/interop limitation rather than a
   remote security hole — but usernames with those characters silently fail.

2. Weak prefix check in `process_server_final` (cosmetic, not a bypass).
   The guard `(data[0] != 'v' && data[1] != '=')` uses `&&` where `||` was
   intended, so a malformed `v=` prefix is not rejected here. It does not
   matter for safety: a bad prefix just yields a garbage verifier that fails
   the subsequent `memcmp`, so auth still fails closed. No OOB read (guarded
   by `strlen(data) < 3`).

3. New transitive OpenSSL include in a public installed header (minor
   API-surface change). `irc-servers.h` is installed and now `#include`s
   `scram.h` which `#include`s `<openssl/evp.h>`. OpenSSL is already an
   unconditional hard dependency of irssi, so the in-tree build and Perl
   bindings are unaffected. Out-of-tree modules/scripts that include the
   installed `irc-servers.h` will now need OpenSSL headers on their include
   path. Worth noting but not a build regression for the release artifact.

4. Behavior change for unknown SASL mechanism names (intended, low risk).
   Previously an unrecognized `sasl_mechanism` only logged a warning and
   left `conn->sasl_mechanism` at its default (PLAIN). Now it is set to the
   `SASL_MECHANISM_MAX` sentinel, which `sasl_start` turns into an explicit
   "Unsupported SASL mechanism" failure + end of negotiation. This is more
   correct, but it is a default-behavior change: a misconfigured mechanism
   name no longer silently attempts PLAIN. Acceptable, just flagged.

`g_critical` on session-create failure does not abort under default GLib
settings, and that path is effectively unreachable for the three supported
digests.
