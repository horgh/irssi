# #1518 — Fix a glib deprecation in module loading, which may allow loading Apple dylibs with new enough glib

- Commit: 7b56ffdc
- Verdict: MINOR

## What it changes
Adds a GLib >= 2.75 code path to `module_open()` in `src/core/modules-load.c`.
On new glib, `g_module_open()` itself constructs the system-dependent module
filename (the prefix/suffix decoration), so `g_module_build_path()` (now
deprecated) and the pre-flight `stat()` are dropped: the raw `name` is handed
directly to `g_module_open()`, first under `<irssi_dir>/modules/`, then under
`MODULEDIR`. This is the change that may allow `.dylib` loading on Apple. The
old `g_module_build_path()` + `stat()` logic is preserved verbatim under
`#else` for GLib < 2.75.

Because the new path can no longer cheaply `stat()` to tell "file not present"
apart from "file present but failed to open", the `module_open()` signature
drops its `int *found` out-param, and `module_load_name()` is reduced from a
tri-state return (`1` ok / `0` found-but-error / `-1` not-found) to a bi-state
(`1` ok / `0` not). Consequently the prefix-fallback guard in
`module_load_full()` changes from `status == -1` to `status <= 0`, and the
"print error even when silent if the file was found" special case
(`!silent || found`) is removed (now just `!silent`).

## Files touched
- src/core/modules-load.c

## Release-safety findings
- Module-load functionality itself is intact; the GLib >= 2.75 path is sound and
  matches glib's documented behavior, and the < 2.75 path is unchanged. No
  crash, memory, UB, or security/injection concern: paths are built with
  `g_strdup_printf`/`g_module_build_path` from existing inputs, no new external
  input or shell/exec surface.

- Behavior change in error reporting (MINOR). Collapsing the tri-state return
  and switching the fallback guard to `status <= 0` means that when a top-level
  module exists but fails to load — most notably an ABI version mismatch, but
  also a dlopen failure or an "invalid" module — `module_load_full()` now also
  runs the prefix fallback (`<module>_core`, `fe_<module>`, ...). Two
  user-visible regressions follow:
  - For a top-level module that fails `g_module_open()` on the (silent) first
    attempt, the real `MODULE_ERROR_LOAD` message (the actual dlopen error
    string) is now suppressed and replaced by a misleading "can't load
    `<module>_core`" error from the fallback's final non-silent attempt.
  - For an ABI-version-mismatch (or invalid-symbol) module, the genuine
    version-mismatch error still prints, but the user now additionally sees a
    spurious load error for a `<module>_core` that was never meant to exist.
  The ABI-mismatch case is common when upgrading irssi while stale third-party
  modules remain installed, so 1.5.0 upgraders may see confusing/duplicated
  module-load errors. This is cosmetic/UX noise only — loading of valid modules
  is unaffected and there is no functional breakage. Not a release blocker.

## Interactions with related changes
None. The change is self-contained in `src/core/modules-load.c`; `module_open`
and `module_load_name` are file-static with no external callers, and the public
`module_load`/`module_load_sub` signatures and return contracts are unchanged.

## NEWS accuracy
Accurate. The NEWS line describes the glib-deprecation fix and the Apple-dylib
possibility, which is the headline change. It does not mention the secondary
change to error-reporting/fallback semantics, but that is a minor side effect
rather than a separate feature.
