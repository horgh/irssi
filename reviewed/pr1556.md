# #1556 — Fix SASL negotiation failing when multiple CAP ACK lines are received

- Commit: 23ec63ae
- Verdict: SAFE

## What it changes
A one-line fix in the `CAP ACK` branch of `event_cap()`. Previously `got_sasl`
was initialized to `FALSE` on every ACK line. Now it is initialized to whether
`sasl` is already present in `server->cap_active`:

    int got_sasl = (i_slist_find_string(server->cap_active, "sasl") != NULL);

When a server splits its CAP ACKs across multiple lines (e.g. `CAP * ACK
:sasl` followed by a second `CAP * ACK :other-cap`), the first ACK line adds
`sasl` to `cap_active` and sets `got_sasl = TRUE`, correctly deferring
`irc_cap_finish_negotiation()` to the SASL handlers. The bug was that a
subsequent ACK line (without `sasl`) reset `got_sasl` to FALSE and called
`irc_cap_finish_negotiation()` (sending `CAP END`) before the SASL handshake
completed, aborting authentication. Seeding `got_sasl` from `cap_active` makes
later ACK lines remember that SASL is still in progress.

## Files touched
- src/irc/core/irc-cap.c

## Release-safety findings
None — safe to release.

The fix is minimal, defensive, and correct:
- `i_slist_find_string` uses exact `g_strcmp0` matching, consistent with the
  existing `strcmp(caps[i], "sasl")` check at line 249, so casing behavior is
  unchanged.
- It does not introduce a hang risk for the common single-ACK case. `got_sasl`
  can only become TRUE-by-default when `sasl` is already in `cap_active`, which
  only happens when an earlier ACK acked it and SASL is genuinely in flight; in
  that case finishing negotiation is correctly owned by the SASL handlers in
  sasl.c (903/902/904-907/907, the timeout, or `AUTHENTICATE *`), all of which
  call `irc_cap_finish_negotiation()`.
- A server-sent `-sasl` removes `sasl` from `cap_active` (lines 243-245) before
  the `got_sasl` re-check on later lines, so de-negotiation is not blocked.
- `irc_cap_finish_negotiation()` is idempotent (guarded by `cap_complete`), so
  no double `CAP END` results.
- No memory management, allocation, or injection surface is affected (read-only
  list lookup; the acked cap strings are still emitted via `cap_emit_signal`
  exactly as before).
