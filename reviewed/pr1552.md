# #1552 — Fix uninitialised memory in the CTCP ping reply

- Commit: 85bb6ef0
- Verdict: SAFE

## What it changes
In `ctcp_ping_reply()`, the local `gint64 tv2` is now initialised to `0`
(`gint64 tv, tv2 = 0;`). The rest of the diff is pure reformatting: the
function signature and the `printformat()` call are rewrapped, with no
behavioral change.

The bug being fixed: a CTCP PING reply is parsed with
`sscanf(data, "%lld %lld", &tv, &tv2)`. The error branch only triggers when
the result is `< 1`, i.e. when not even the first field (`tv`) is parsed. If
the reply contains exactly one numeric field, `sscanf` returns `1`, the error
branch is skipped, and `tv2` was used uninitialised at
`tv2 += tv * G_TIME_SPAN_SECOND;`. Initialising `tv2 = 0` makes that case
deterministic.

## Files touched
- src/fe-common/irc/fe-ctcp.c

## Release-safety findings
None — safe to release.

The fix is minimal and correct. `tv` is always populated when the error
branch is not taken (it is the first conversion, guaranteed set whenever
`sscanf >= 1`), so it does not need initialising. With `tv2 = 0`, a one-field
reply now computes a defined `usecs` value instead of reading stack garbage;
this only affects the displayed ping time for a malformed/short reply and
cannot crash or corrupt anything. No new inputs, allocations, or branches are
introduced, so there is no injection or memory-management risk. The
reformatting does not alter the emitted format string or argument order.

## Interactions with related changes
None. The change is confined to the front-end reply handler. The core
`ctcp_ping` request handler in src/irc/core/ctcp.c is a separate function and
is unaffected.

## NEWS accuracy
Accurate. The change initialises previously-uninitialised memory (`tv2`) used
in the CTCP ping reply path, exactly as described.
