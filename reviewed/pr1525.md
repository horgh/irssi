# #1525 — Fix the /BAN command, which was broken by an earlier change

- Commit: 5c159375
- Verdict: MINOR

## What it changes
Fixes the ban list display used by the `/BAN` command (`bans_show_channel`
in fe-irc-commands.c). An earlier change (201296a0) extended the
`banlist_long` format to require 6 arguments (`$0` counter int, `$1` channel,
`$2` ban, `$3` setby, `$4` "ago" string, `$5` timestamp string) and updated
`event_ban_list` accordingly, but did NOT update `bans_show_channel`. As a
result `/BAN` (the local ban listing) still passed only 5 args with the 5th
being `(int)(time(NULL)-rec->time)`. Because the format declares `$4` as
FORMAT_STRING, `format_read_arglist` did `va_arg(va, char*)` on that int and
also read a non-existent 6th vararg, then treated both as `char*` and printed
them — i.e. undefined behavior / likely crash on `/BAN`.

The fix:
- Moves `time_ago()` from being a static helper in fe-events-numeric.c into
  fe-irc-channels.c and exports it via fe-irc-channels.h (body unchanged).
- Updates `bans_show_channel` to compute `timestr = my_asctime(rec->time)`
  and `ago = time_ago(rec->time)` and pass all six arguments in the correct
  types, matching the format declaration and `event_ban_list`.
- Bumps `IRSSI_ABI_VERSION` 53 -> 54 (new exported symbol `time_ago`).

## Release-safety findings
- The core fix is correct and removes a real crash/UB on the `/BAN` listing
  path. Argument count and types now match the `banlist_long` /
  `banlist` format declarations (`{1,0,0,0,0,0}` and `{1,0,0}`). The short
  `banlist` format reads only the first 3 args; the extra args are harmless.
- MINOR memory leak: `timestr = my_asctime(rec->time)` returns a g_strdup'd
  string that is never freed in `bans_show_channel`'s loop. `event_ban_list`
  frees its equivalent `timestr` (g_free at line 165); the new code does not.
  `ago` comes from `time_ago`'s static buffer and correctly is not freed.
  The leak is bounded by the number of bans displayed and only occurs on a
  user-invoked `/BAN` listing, so it is not a release blocker, but it is a
  genuine per-ban-per-invocation leak.
- ABI bump to 54 is appropriate for the newly exported `time_ago` symbol;
  modules will correctly require recompilation. Master has since advanced to
  58, so this intermediate value causes no conflict.
- No symbol collision for the now-public `time_ago`; `time_t` is already in
  scope in every file including the header. No build/portability regression.
- No injection or security concern: only timestamp/duration strings derived
  from existing ban records are formatted through the normal printformat path.

## Interactions with related changes
The bug originated from sibling change 201296a0 ("add time_ago()"), which
updated the server-numeric ban display but missed the local `/BAN` command
path; this commit completes that work. Consistent with `event_ban_list`.
The ABI bump is part of the normal 1.5.0 ABI-version sequence (later commits
raise it further to 58) and does not conflict.

Accurate. The change fixes the `/BAN` command's ban listing, which was broken
