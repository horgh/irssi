# #1542 — Use EAI_NONAME instead of HOST_NOT_FOUND for getaddrinfo(3) errors

- Commit: a5441f62
- Verdict: SAFE

## What it changes
A single-line change in `src/core/network.c`. Inside the (then) getaddrinfo(3)-based
`int net_gethostbyname()`, the "no addresses found" fallback return value was changed
from `HOST_NOT_FOUND` to `EAI_NONAME`:

    if (count_v4 == 0 && count_v6 == 0)
    -    return HOST_NOT_FOUND; /* shouldn't happen? */
    +    return EAI_NONAME; /* shouldn't happen? */

This is correct in its own context: the surrounding function returns `getaddrinfo()`
status codes (e.g. `EAI_NONAME`), which are decoded with `gai_strerror()`.
`HOST_NOT_FOUND` is an `h_errno`/`hstrerror()` value and was the wrong namespace to
mix into a getaddrinfo return path. The branch is also a "shouldn't happen" fallback,
so it is rarely (if ever) hit in practice.

## Files touched
- src/core/network.c (1 line)

## Release-safety findings
None — safe to release.

Important context: the function this change modified no longer exists at the 1.5.0
release state. A later, also-in-1.5.0, set of changes ("use GIO resolver", #1580,
with follow-ups #1605/#1607) rewrote `net_gethostbyname()` to use GLib's `GResolver`
and removed the getaddrinfo(3) code path entirely. On master, `EAI_NONAME` and
`HOST_NOT_FOUND` no longer appear anywhere under `src/` (verified by grep). Because
#1580 merges after #1542 on master's first-parent history and supersedes the same
lines, #1542 is effectively a no-op in the shipped 1.5.0 code. It cannot break
anything because the code it touched is gone.

The change itself introduces no bugs, no behavior change for users (it was an
unreachable-ish "shouldn't happen" path and is now removed regardless), no memory/UB
issues, no security/injection surface, and no ABI/build concerns (`EAI_NONAME` is a
standard POSIX getaddrinfo macro, already used; `net_gethostbyname` here was
file-static).

## Interactions with related changes
- #1580 (use GIO resolver) and its follow-ups #1605/#1607 rewrote/removed the exact
  function and line that #1542 modified. They land after #1542 on master and override
  it; there is no conflict, but #1542 has no surviving effect once #1580 is applied.
- #1541 (inet_pton) and #1445 (prefer IPv6) touch the same resolver area but do not
  interact with this specific line.
- No ordering dependency that affects safety: whether #1542 is present or not, the
  released code is identical after #1580.

Separate, pre-existing observation (NOT caused by #1542, out of scope): in current
master `src/core/capsicum.c:282` still calls `net_gethostbyname(addr, &ip4, &ip6)`
(3-arg, int return) while `network.c`/`network.h` now only provide a 2-arg
`GResolver`-based static `net_gethostbyname` and `net_gethostbyname_first_ips`. That
mismatch in the `HAVE_CAPSICUM` (FreeBSD) build is an artifact of the GResolver
rewrite, not of this change, and should be evaluated under the #1580/#1605/#1607
review rather than here.

merged. However, it describes a change that has no effect in the released 1.5.0 code,
