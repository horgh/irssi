# #1405 — Fix a crash when loading a server set up without a chatnet

- Commit: 555030a2
- Verdict: SAFE

## What it changes
Refactors `server_setup_read()` in `src/core/servers-setup.c` to compute the
chat protocol (`proto`) explicitly instead of relying on
`CHAT_PROTOCOL(chatnetrec)` at the point of use.

The fix is for the `chatnet == NULL` case. Previously, with no chatnet,
`chatnetrec` stayed NULL and the code did
`CHAT_PROTOCOL(chatnetrec)->create_server_setup()`. The `CHAT_PROTOCOL(NULL)`
macro evaluates to `chat_protocol_get_default()`, which returns NULL when no
chat protocols are loaded (`default_proto == NULL`). Dereferencing that NULL
crashed.

The new code splits into three branches:
- `chatnet != NULL` and found: `proto = CHAT_PROTOCOL(chatnetrec)` (unchanged
  semantics).
- `chatnet != NULL` and not found: create it via the default protocol (same as
  before; guarded by the pre-existing `chatnet_find_unavailable()` early
  return, which itself returns TRUE if the default protocol is NULL).
- `chatnet == NULL`: `proto = chat_protocol_get_default()`, and if `proto ==
  NULL`, return NULL early ("no protocols loaded, skip loading servers"). This
  is the new guard that prevents the crash.

`proto->create_server_setup()` and `rec->chat_type = proto->id` then use the
resolved (non-NULL in every reachable path) protocol. Also a cosmetic
reformat of the `family` ternary.

## Files touched
- src/core/servers-setup.c

## Release-safety findings
None — safe to release.

- In all three branches `proto` is guaranteed non-NULL before it is
  dereferenced: the `chatnet==NULL` branch returns early on NULL; the
  create branch is reachable only when `chatnet_find_unavailable()` returned
  FALSE, which implies `chat_protocol_get_default()` is non-NULL; the
  found branch preserves the prior behavior exactly.
- `rec->chatnet = chatnetrec == NULL ? NULL : g_strdup(...)` still correctly
  handles the NULL `chatnetrec` case, so no NULL deref or stray allocation.
- The early NULL return is harmless: the sole caller (the config read loop at
  line ~752) ignores the return value, so the entry is simply skipped, which
  is the intended behavior. The preceding `server_setup_remove()` of a
  duplicate before an early return is pre-existing behavior, not introduced
  here.
- The potential NULL deref in the found-chatnet branch (if a chatnet's
  protocol were unregistered) is identical to the pre-fix code and is not a
  regression from this change.
- No injection / input-validation surface: inputs are config values handled
  the same as before. No ABI/build/portability impact (single function,
  internal logic only).

## NEWS accuracy
Accurate. The change fixes a crash that occurred when loading a server setup

default / loaded).
