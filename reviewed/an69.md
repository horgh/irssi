# an#69, 3a5f93bb — Remove the enable-true-color compile-time switch and always enable 24-bit true color

- Commit: 3a5f93bb
- Verdict: MINOR

## What it changes
Removes the `enable-true-color` meson option and the `TERM_TRUECOLOR` compile-time
conditional. The `TERM_TRUECOLOR` config define is hard-set to `true` in
`meson.build`, and all `#ifdef TERM_TRUECOLOR` / `#else` branches in the C sources
are collapsed to the truecolor-enabled path. The dead non-truecolor branches are
deleted (including the static helper `color_24bit_256_int` and the
non-truecolor-signature `term_set_color` declaration). The Termux CI workflow stops
passing `-Denable-true-color=yes`.

Net effect on the shipped binary: the 24-bit color code path is now always compiled
in. Runtime behavior is unchanged for users who have not enabled it, because output
is still gated by the `colors_ansi_24bit` setting (default `FALSE`):
`term_use_colors24` is `settings_get_bool("colors_ansi_24bit") && ...`, and
`termctl_set_color_24bit()` falls back to the 256-color approximation
(`color_24bit_256()`) when `term_use_colors24` is off. The `gui_printtext`
mirc-to-24bit map (`use_24_map`) is likewise still driven by that setting.

## Release-safety findings
No release-safety issue in the shipped product. Verified specifically:

- Default runtime behavior is preserved. Before the change a default *meson* build
  actually compiled with truecolor OFF (the `enable-true-color` combo had
  `choices : ['no', 'yes']` and no explicit `value`, so meson defaults to the first
  choice, `no`). After the change the code is always compiled in, but actual 24-bit
  terminal output is still opt-in via `colors_ansi_24bit` (default `FALSE`) and
  downgrades to 256-color when off. So users see no change unless they had explicitly
  enabled the setting.
- No dangling references. The deleted `#else` helper `color_24bit_256_int` had its
  only caller removed; `color_24bit_256` is still used in `term-terminfo.c`, so no
  unused-function/variable regression. `rgb[]` in `format_24bit_color` is now used in
  the retained body. No `#ifdef TERM_TRUECOLOR` remain in the tree.
- No public ABI impact. `term_set_color` / `term_set_color2` live in `term.c` /
  `term-terminfo.c`, which compile into the `irssi` executable (fe-text), not an
  installed shared library. They are not part of the module/Perl ABI, which is
  governed by `IRSSI_ABI_VERSION` in `src/common.h` (= 45, correctly unchanged). The
  switch of the exported terminal symbol from `term_set_color` to `term_set_color2`
  for a default build is internal to the binary only.
- `TERM_TRUECOLOR` is still `#define`d (set to `true`), so any external/module code
  testing `#ifdef TERM_TRUECOLOR` continues to behave as in a truecolor build.

CI-only (not a release blocker): `.github/workflows/abicheck.yml` still passes
`-Denable-true-color=yes` directly to `meson setup` (line 4, used at lines 29 and 63),
and that option no longer exists. The workflow pins `meson<0.59.0`, where an unknown
`-Doption` is a hard error, so the abicheck job is likely to fail until the workflow
is updated. This affects CI only — it does not touch the released source/binary — so
it is a MINOR/process issue, not a shipping concern.
