# #1450 — Fix a crash on connect during startup when no chat protocol is available

- Commit: d627e560
- Verdict: SAFE

## What it changes
Adds an early-return guard in `create_addr_conn()` (src/core/servers-setup.c). When
no chat protocol can be resolved (`proto == NULL`, i.e. `chat_protocol_get_default()`
returned NULL because no protocol module is loaded), it now calls `signal_stop()` and
returns NULL before the pre-existing `g_return_val_if_fail(proto != NULL, NULL)`.

The `signal_stop()` is the meaningful part: `create_addr_conn` is reached from
`cmd_connect` while the "command connect" signal is being emitted (both for startup
autoconnect, which does `signal_emit("command connect", ...)` directly, and for a
user-typed `/connect`, which dispatches through `commands.c` at line 920). Stopping
the signal makes `signal_emit("command connect", ...)` return TRUE, which prevents
`signal_default_command` from firing in `commands.c` — i.e. it suppresses a spurious
"unknown command" emission for a command that is in fact known. `cmd_connect` still
continues normally after the NULL return and emits `CMDERR_NO_SERVER_DEFINED` to the
user. The change is a defensive fix; the commit message itself notes it does not make
connecting actually work in this no-protocol state.

## Files touched
- src/core/servers-setup.c (+5 lines)

## Release-safety findings
None — safe to release.

The guard is correctly scoped:
- It only triggers when `proto == NULL`, which without a guard would lead to a NULL
  deref at `proto->create_server_connect()` (the pre-existing `g_return_val_if_fail`
  protects against this only when GLib checks are enabled; the new explicit return is
  strictly safer and is now the operative check, leaving the old macro as dead code —
  harmless).
- `signal_stop()` is safe in every reachable call path. The two production callers of
  `create_addr_conn` are `cmd_connect`/`get_server_connect` (the intended path, inside
  the "command connect" emission) and `session_restore_server` (which passes a
  non-NULL `proto->id`, so `chat_protocol_find_id` resolves it and the new branch is
  not reached). If `signal_stop()` were ever called with no signal emitting, it only
  logs a `g_warning` — no crash.
- No new allocation, no memory/ownership change, no leak (NULL is returned before any
  `conn` is created/ref'd), no injection surface, no ABI/default/portability change.

## Interactions with related changes
None. Single isolated guard in one function; no shared state or sibling-change overlap.

## NEWS accuracy
Accurate. The line ("Fix a crash on connect during startup when no chat protocol is
available") matches the change. Worth noting only that the upstream fix is partial —
it stops the crash and the misleading error but does not make connecting succeed in
the no-protocol state — but that does not affect the accuracy of the NEWS entry for
release-safety purposes.
