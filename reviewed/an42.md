# an#42, d9b181e4 — Autoload the IRC protocol module and load its config when the chat protocol is created

- Commit: d9b181e4
- Verdict: NEEDS_ATTENTION

## What it changes
This is a large architectural change (merge of PR ailin-nemui#42, "Protocol module
autoloading"), not the small one-liner the NEWS entry suggests. It converts the IRC
protocol and its sub-modules (dcc, flood, notifylist, fe_common_irc, fe_irc_dcc,
fe_irc_notifylist) from statically-linked-into-the-binary code into dynamically
loaded shared modules, following the same pattern already used for perl
(`#ifdef HAVE_STATIC_PERL`, a symbol never actually defined by the build).

Concretely:
- `fe-text`/`fe-none` no longer link `libirc_a`/`libfe_common_irc_a` etc.; all the
  `irc_init()`/`fe_irc_modules_init()` static-init call sites are wrapped in
  `#ifdef HAVE_STATIC_IRC` (also never defined), so they compile out. IRC is now
  pulled in purely via the `autoload_modules` setting.
- The default for `autoload_modules` changes from `"perl otr"` to
  `"irc dcc flood notifylist perl otr"`.
- `irc_core_init()` now registers the IRC chat protocol *last* (after all of
  `irc_*_init()` and `settings_check()`), instead of first.
- New "deferred config" mechanism: `core_init()` adds `reread_setup` to
  `setup reread`, `irssi init read settings`, and (the key bit)
  `signal_add_last("chat protocol created", ...)`. `reread_setup` emits the new
  per-area signals `setup reread chatnets|servers|channels`. chatnets/servers/
  channels setup readers were re-pointed from the old generic `setup reread` /
  `irssi init read settings` signals to these new specific signals.
- chatnets that reference a not-yet-loaded protocol are recorded in a new
  `chatnets_unavailable` list instead of being created as "unknown" protocol
  records; `chatnet_find_unavailable()` is added and used by `server_setup_read()`
  to skip server entries whose protocol is not loaded yet. When the IRC module
  finally registers its protocol, "chat protocol created" fires and the config is
  re-read with IRC now available.
- `chat_protocol_register()` now destroys a pre-existing `not_initialized` (dummy)
  record before re-registering; `chat_protocol_get_unknown()` no longer assigns
  `create_server_connect`/`destroy_server_connect` (commented out -> left NULL).
- `chat_protocol_lookup()` returns the new sentinel `CHAT_PROTOCOL_NOT_INITIALIZED`
  (-2) for dummy protocols; `perl_register_protocol()` bails out on that.
- ABI version bumped 44 -> 45. Several meson targets become `shared_module`s; a new
  Termux package CI workflow is added; fuzz/test targets re-pointed from `libirc_a`
  to `libirc_core_a` (+ `libirc_flood_a`).

## Release-safety findings

1. Upgrade compatibility of the `autoload_modules` default change (most important).
   Because IRC is now loaded *only* via `autoload_modules`, and the default changed
   to include `irc dcc flood notifylist`, this works for users on the stock default.
   But any user who has previously *customized* `autoload_modules` (a common thing —
   e.g. to add a third-party module, having written `/set autoload_modules perl otr
   mymodule`) has that value persisted in their config, and irssi uses the saved
   value, not the new default. For those users `irc` (and dcc/flood/notifylist) will
   silently not load on first run of 1.5.0, leaving a client with no IRC support and
   no obvious error pointing at the cause. There is no migration/compatibility
   shim in the diff. This is an intentional design tradeoff of the redesign rather
   than a code bug, but it can break existing installs on upgrade and warrants a
   release note / migration handling.

2. Dummy "unknown" protocol now has NULL create/destroy_server_connect (latent
   NULL function-pointer call). `chat_protocol_get_unknown()` leaves
   `create_server_connect`/`destroy_server_connect` NULL (previously they were safe
   stubs). `create_addr_conn()` calls `proto->create_server_connect()` and
   `server_connect_unref()` calls `CHAT_PROTOCOL(conn)->destroy_server_connect(conn)`
   with no NULL check. The common reachable paths are guarded:
   - `chat_protocol_find_net()` never returns a dummy (its `chatnet` field is NULL),
   - `server_setup_read()` now skips unavailable-protocol servers, so a dummy's id
     never ends up in `setupservers`/`bestrec->chat_type`,
   - session.c and windows-layout.c check `not_initialized`.
   The residual risk is the unregister-then-reconnect path: a dummy is recreated by
   `chat_protocol_unregister()` (i.e. after a module is unloaded), so unloading the
   irc module while config still references it and then triggering a connect could
   reach a NULL `create_server_connect`/`destroy_server_connect`. This is an edge
   case (manual module unload) and a behavioral regression vs. the old safe stubs,
   not something a normal user hits, so MINOR — but it would be safer to keep the
   stub functions or add NULL guards at the two call sites.

3. Note on the `not_initialized` guard in chat-commands.c (cmd_connect, line ~87):
   it runs *after* `server_create_conn_opt()` has already constructed `conn`. With
   the dummy now having a NULL `create_server_connect`, that earlier construction
   would itself crash before the guard is reached if a dummy proto were ever used —
   i.e. the guard's safety depends entirely on a dummy id never reaching
   `create_addr_conn`. The skip logic in `server_setup_read()` plus
   `chat_protocol_find_net()` returning NULL for dummies is what upholds this; it
   holds for the default config but the invariant is implicit and fragile.

No memory-corruption, injection, or other security issue found in the core logic.
The init sequencing (read settings -> records IRC config as unavailable -> module
autoload loads irc -> "chat protocol created" -> reread loads the IRC config ->
autoconnect) is internally consistent and does not recurse (the reread signals do
not re-emit "chat protocol created"). The meson `dl_cross_irc_*` variables are
defined (in src/irc/*) before they are consumed (src/fe-common/irc/*, src/perl/irc),
matching the subdir ordering in src/meson.build. ABI bump to 45 correctly prevents
stale modules from loading.

## Interactions with related changes
The new `setup reread chatnets|servers|channels` signals replace direct use of the
generic `setup reread` and `irssi init read settings` signals in chatnets-setup,
servers-setup, and channels-setup. Any out-of-tree code or sibling change that still
emits/handles the old generic signals expecting these readers to fire will no longer
trigger them (core now bridges old -> new via `reread_setup`). Perl protocol
registration depends on the new `CHAT_PROTOCOL_NOT_INITIALIZED` sentinel. The fuzz
and flood tests were re-pointed to `libirc_core_a`/`libirc_flood_a`, consistent with
the removal of the aggregate `libirc_a`.

## NEWS accuracy
Materially understated. The NEWS line ("Autoload the IRC protocol module and load
its config when the chat protocol is created") describes only the user-visible intent
of the change. The actual change is a broad refactor: it makes IRC a dynamically
loaded module (removing it from the statically linked binary), changes the default
`autoload_modules` value, bumps the ABI version (44->45), introduces new public-ish
signals, and adds a Termux CI workflow. The ABI bump and the `autoload_modules`
default change in particular have user-facing/upgrade impact that the NEWS entry does
not mention.
