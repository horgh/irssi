# an#79, ae5a9283 — Fix bound IRC queries not being restored on reconnect

- Commit: ae5a9283
- Verdict: SAFE

## What it changes
Adds a "server connected" signal handler `sig_window_bound_query` in the IRC
frontend (`src/fe-common/irc/fe-irc-queries.c`). On connect to an IRC server it
walks every window's `bound_items` and, for each bind whose `type` equals the
QUERY window-item type and whose `servertag` matches the connected server,
calls `irc_query_create()` to recreate the query. A file-scope global
`int query_type` is cached in `fe_irc_queries_init()` via
`module_get_uniq_id_str("WINDOW ITEM TYPE", "QUERY")`, the new signal is added
in init and removed in deinit, and three includes are added
(irc-servers.h, irc-queries.h, fe-windows.h). `IRSSI_ABI_VERSION` is bumped
45 -> 46.

These QUERY-typed binds are produced only by layout restore
(`windows-layout.c:75`) when the IRC protocol module is not yet initialized at
restore time — i.e. a `/LAYOUT SAVE`d query window that has a binding but no
live query object yet. The handler recreates the query so it reattaches to its
saved window on connect.

## Files touched
- src/common.h (ABI version bump 45 -> 46)

## Release-safety findings
None — safe to release.

Items considered and cleared:

- Iteration safety / use-after-free: `irc_query_create()` emits "query created"
  -> `signal_query_created` -> `window_item_create`, which finds the matching
  (name, tag) bind and destroys it when non-sticky, mutating
  `win->bound_items` mid-loop. The code defends against this with
  `g_slist_copy()`; only the bind matching the just-created query is destroyed
  (binds are unique per name+tag), and the copied list nodes are not freed
  until `g_slist_free(bounds)`. No dangling traversal.

- Duplicate queries: `irc_query_create`/`query_init` do not dedup, but a
  duplicate cannot arise in the real flows. The layout-restore QUERY bind is
  non-sticky, so it is consumed by `window_item_create` on the first connect
  and does not re-fire on later reconnects. The newly created query has
  `server` set (via `server_find_tag` in `query_init`), so the other
  "server connected" handler (`sig_server_connected` in fe-queries.c, guarded
  by `rec->server == NULL`) skips it and does not double-add it to
  `server->queries`.

- No interference with existing runtime behavior: the only runtime creator of a
  query bind, `signal_query_destroyed` (fe-queries.c:105, the `unwanted`/DCC
  case), calls `window_bind_add` without setting `rec->type`, leaving it 0. The
  new handler matches only `type == query_type`, so it ignores those binds.

- No symbol collision: the other `query_type` occurrences (fe-common-core.c,
  channels-query.c) are local variables, not externally linked globals, so the
  new file-scope `int query_type;` does not clash at link time.

- No network/injection surface: restoring a query is purely local UI state.
  "query created" handlers only touch windows; none emit IRC commands. `name`
  and `servertag` are guaranteed non-NULL by `window_bind_add`, and
  `irc_query_create` g_return-guards a NULL nick. No attacker-controlled data
  reaches a protocol command.

- `IS_IRC_SERVER(server)` safely rejects non-IRC and NULL servers; the early
  return is correct. ABI bump is appropriate for the behavior change (current
  master is at 58, so this bump was later superseded — not a concern).

Minor robustness note (not a release issue): `irc_query_create` relies on the
invariant that a QUERY-typed `bound_item` never coexists with a live query of
the same (name, tag). That invariant holds for the layout-restore path that
produces these binds, so no guard is needed in practice.

## Interactions with related changes
None. The handler is additive and self-contained within the IRC frontend; it
coexists cleanly with the existing core `sig_server_connected` query-reattach
logic in fe-queries.c (different guards, no overlap).

## NEWS accuracy
Accurate. The NEWS line ("Fix bound IRC queries not being restored on
reconnect") matches the behavior: query window bindings that previously had no
query recreated on (re)connect now get their query restored. Scope is slightly
narrower than the wording might suggest — it restores QUERY-typed window binds
(those from layout restore), not arbitrary lost queries — but that is the
intended fix and is consistent with the description.
