# #1523 — Fix irssi switching to a Unix socket when the network name contains a slash

- Commit: 4b48cdce
- Verdict: SAFE

## What it changes
In `get_server_connect()` (the helper backing `/CONNECT` and `/SERVER`),
the heuristic that decides whether the target is a Unix-domain socket was:

    if (strchr(addr, '/') != NULL)
        conn->unix_socket = TRUE;

It now also requires that the address is not a known chat network:

    if (strchr(addr, '/') != NULL && chatnet_find(addr) == NULL)
        conn->unix_socket = TRUE;

A new `#include <irssi/src/core/chatnets.h>` is added for `chatnet_find()`.
The effect: when a configured network whose name contains a `/` (e.g.
`foo/bar`) is passed, irssi no longer mis-flags the connection as a Unix
socket and instead connects to the network's real server via TCP.

## Files touched
- /home/ubuntu/irssi/src/core/chat-commands.c (2 insertions, 1 deletion)

## Release-safety findings
None — safe to release.

Verification notes:
- No NULL deref: `addr` is validated non-NULL and non-empty earlier in the
  function (chat-commands.c:53-60), and `chatnet_find()` itself guards
  `name != NULL` (chatnets.c:105). `conn` is also guaranteed non-NULL here
  (the `conn == NULL` case returns at chat-commands.c:77-82).
- No memory/lifetime issue: `chatnet_find()` returns a borrowed pointer and
  the result is only compared against NULL, not stored or freed.
- No injection/security concern: the added check is a case-insensitive name
  comparison (`g_ascii_strcasecmp`) against the in-memory list of configured
  chat networks; no parsing, exec, or external input handling is introduced.
- Consistent with existing precedence: `server_create_conn_opt()` already
  resolves `dest`/`addr` via `chatnet_find()` first (servers-setup.c:403) and
  routes a matched chatnet through `create_chatnet_conn()`, where the real
  server address (not the chatnet name) is what reaches the slash-based
  socket check in `server_setup_fill()` (servers-setup.c:158-159). The new
  guard simply prevents the later, redundant socket flag in chat-commands.c
  from contradicting that resolution. Both call sites use the same
  `chatnet_find(addr)`, so they cannot disagree.
- Behavior change is limited to the bug being fixed. The only theoretical
  regression would be a user who has a real Unix-socket path that is
  byte-for-byte identical to a configured chatnet name containing a slash; in
  that case the chatnet interpretation now wins. This is an extreme,
  unrealistic collision and matches the more sensible precedence, so it is
  not a release concern.
- No ABI/build/portability impact: only an added include of an existing
  internal header.

## Interactions with related changes
None. The reconnect paths that also set `unix_socket` based on a slash
(servers-reconnect.c:281, servers-setup.c:159) operate on the already-resolved
real server `conn->address`, not on the user-typed chatnet name, so they
remain correct and consistent with this fix.
