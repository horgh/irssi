# #1491 — Fix a crash when adding a server

- Commit: 58ca3af3
- Verdict: SAFE

## What it changes
In `create_server_setup()` (src/fe-common/core/fe-server.c), the code previously
did `server = rec->create_server_setup();` unconditionally. `rec` comes from
`chat_protocol_find_net(optlist)` and, when that returns NULL, falls back to
`chat_protocol_get_default()`. If no chat protocols are loaded,
`chat_protocol_get_default()` returns NULL, so the subsequent `rec->...`
dereferenced a NULL pointer and crashed.

The change adds a `if (rec == NULL)` guard before the dereference. On that path
it emits the existing `chat protocol unknown` signal with `"(none)"` and returns
NULL. The diff also re-indents the two following lines (tabs instead of spaces);
no logic change there.

## Files touched
- src/fe-common/core/fe-server.c

## Release-safety findings
None — safe to release.

- The new NULL branch is reached only when `rec == NULL` (no protocols / no
  default), exactly the case that crashed before; behavior is otherwise
  unchanged.
- The emitted signal `"chat protocol unknown"` is registered in this same file
  (signal_add in fe_server_init) and handled by `sig_chat_protocol_unknown`,
  which only `g_return_if_fail(protocol != NULL)` and printformats. The passed
  argument `"(none)"` is a non-NULL string literal, so the handler is safe.
- The single caller, `cmd_server_add_modify()`, already checks the NULL return
  (frees `free_arg` and returns), so returning NULL here is handled cleanly with
  no leak or further dereference.
- No new allocation, no ownership/lifetime change, no ABI or build/portability
  impact. No user input is incorporated into the signal argument, so no
  injection concern.

None.

## NEWS accuracy
Accurate. The change fixes a crash on `/server add` (via `create_server_setup`)
when no chat protocol is available.
