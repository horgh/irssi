# #1604 — Move the Perl DCC glue into a separate Irssi::Irc::Dcc module so Irssi::Irc can be used with dcc unloaded

- Commit: 3629a122
- Verdict: SAFE

## What it changes
Splits the Perl DCC glue out of the `Irssi::Irc` XS module into its own
loadable module `Irssi::Irc::Dcc`:

- Moves the `perl_dcc_*_fill_hash()` helpers and all DCC XS subs out of
  `Irc.xs` into `Dcc.xs`. The DCC object registrations
  (`irssi_add_object` for Dcc::Chat/Get/Send/Server), the `Irssi::Irc::Dcc`
  plain-object entry, and the `@ISA` setup move from `Irssi::Irc::init()`
  into a new `Irssi::Irc::Dcc::init()`. `Dcc.xs` gains its own
  `init()`/`deinit()`/`BOOT:` following the same pattern as the other XS
  modules.
- Adds `src/perl/irc/Irc/Dcc.pm` as a normal DynaLoader-bootstrapped Perl
  module, installed to `Irssi/Irc/Dcc.pm`.
- `Irc.pm` now does `eval { local $@; require Irssi::Irc::Dcc; 1; }` after
  its own init, so `Irssi::Irc` loads even if the DCC module is absent.
- `meson.build`: `Dcc.xs` is removed from the `Irc` shared library (and the
  `Irc` library no longer links `dl_cross_irc_dcc`); a new `Dcc` shared
  library is built/installed under `auto/Irssi/Irc/Dcc` and links
  `dl_cross_irc_dcc`.
- Bumps `IRSSI_ABI_VERSION` 57 -> 58 and `IRSSI_PERL_API_VERSION` base
  constant 20011214 -> 20160124 (gated by `perl_api_version_check`).
- Restores the global `IPADDR ip4_any` definition in `src/core/network.c`
  that had previously been removed (see findings).

## Release-safety findings
None — safe to release.

Notes from the investigation (all check out):

- ip4_any restoration is a genuine fix, not a risk. At the parent commit
  (3c656846) `ip4_any` was declared `extern` in network.h and referenced in
  dcc.c/dcc-server.c, but had no definition anywhere (it was dropped by an
  earlier "use GIO resolver" commit). The DCC core module thus had an
  undefined symbol on master before this merge. The restored definition is
  byte-for-byte identical to the original pre-removal definition; the
  `IN6ADDR_ANY_INIT`/`{ INADDR_ANY }` init of the `struct in6_addr` field
  yields an all-zero "any" address, which is correct.
- The `BOOT: /* nothing * /` unterminated-comment defect that existed
  transiently AT this merge commit (3629a122) is NOT present in the released
  state: commit 00146211 ("fix space in end comment") corrects it, and that
  fix is in master/HEAD. The trailing newline was the only thing the broken
  comment could have consumed, so it would not have changed generated code
  even at the broken revision.
- No double registration: `Irc.xs` registers `irc_plains` (no Dcc entry);
  `Dcc.xs` registers `irc_dcc_plains` plus the four DCC object types. Clean
  split.
- init/deinit lifecycle is correct. `Dcc.xs` mirrors the existing
  `initialized`-flag pattern and calls `perl_api_version_check`. Perl
  teardown (perl-core.c) iterates `@DynaLoader::dl_modules` calling
  `::deinit()` on each `Irssi*` module, so the new separate module's
  `deinit()` is invoked properly.
- Typemap resolution is preserved. `T_DccObj` lives in the local
  `src/perl/irc/typemap`, which xsubpp auto-discovers from the .xs file's
  directory; the new `Dcc` shared library sits in that same directory and
  uses the identical `-typemap ../common/typemap` argument the `Irc` build
  already used.
- Build wiring is correct: `dl_cross_irc_dcc` is properly defined and only
  linked into the new `Dcc` library; the `Irc` library dropping it is the
  intended decoupling.
- Behavior change is intended and contained: DCC Perl functions
  (`Irssi::Irc::dccs`, `dcc_*`) and DCC object types only exist when the
  `Irssi::Irc::Dcc` module loads. No internal irssi script/doc depends on
  these unconditionally.

## Interactions with related changes
This merge bundles several sibling commits from the same author/cycle:
"restore ip4_any", "make Irssi::Irc usable without dcc", "up perl api",
"up abi". The ABI/perl-API bumps are release-wide values shared with other
1.5.0 perl-group changes (an38, pr1510, pr1543, pr1606); they are
monotonic and the value in master is the final one, so no conflict. No
ordering dependency that affects release safety.
