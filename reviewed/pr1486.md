# #1486 — Add a command_history_editable setting to enable bash-like editing of command history entries

- Commit: 07b971cf
- Verdict: SAFE

## What it changes
Adds a new boolean setting `command_history_editable` (default `FALSE`) registered
in `command_history_init()`. In both `command_history_prev_int()` and
`command_history_next_int()`, when the user navigates away from a history entry
whose displayed text has been modified, the behavior changes only if the setting
is on: instead of appending the edited text as a brand-new entry via
`command_history_add()`, the code edits the entry in place — it frees the old
`HISTORY_ENTRY_REC` (`history_entry_destroy(pos->data)`) and stores a freshly
allocated one (`pos->data = history_entry_new(history, text)`) on the same GList
link. This gives bash-like persistent editing of recalled history lines. When the
setting is off (the default), behavior is identical to before.

## Release-safety findings
None — safe to release.

Notes from the analysis (none rise to a release blocker):

- Memory safety is sound. The in-place edit swaps only `link->data`; the GList
  link node itself is preserved, so `history->pos` and every other GList pointer
  remain valid (no dangling links, no use-after-free). The replacement path is
  guarded by `pos != NULL`, so it never dereferences a NULL `pos->data`. When
  `pos == history->pos` (boundary navigation), the code destroys then immediately
  reassigns `link->data` and the subsequent read of `history->pos->data->text`
  sees the new pointer. `history_entry_new()` does `g_strdup(text)`, so the
  caller's `line` buffer is copied, not aliased; callers (gui-readline.c) use the
  returned string synchronously before freeing their buffer.

- Default is `FALSE`, so existing users see no behavior change. Opt-in only.

- Minor latent issue (not a blocker, opt-in only): in the global-history paths
  (`command_global_history_prev/next`, `global == TRUE`), navigation can position
  `history->pos`/`pos` on an entry belonging to a *different* HISTORY_REC. The
  edit then re-tags that entry to the current window's history via
  `history_entry_new(history, ...)` without adjusting either history's `lines`
  counter, so per-history line counts can drift. The only consequence is a
  slightly inaccurate pruning threshold in `command_history_add()`; no crash or
  memory-safety impact. (Global navigation already crosses histories; this change
  only makes that crossing mutate an entry rather than append a new one.)

- No injection surface: text is stored and later set back into the entry widget;
  it is not interpreted as a command or format string here.

- Read-only consumers (Perl XS bindings in src/perl/ui/Window.xs, special history
  search) only traverse the list and do not depend on append-only or immutable
  entries, so they are unaffected by in-place edits.
