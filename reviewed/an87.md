# an#87, 7285da27 — Fix /names sending a raw server event by binding it first

- Commit: 7285da27
- Verdict: SAFE

## What it changes
A single-line change in `fe_channels_init()`: the `/names` command handler in
fe-common is registered with `command_bind_first(...)` instead of
`command_bind(...)`. This raises its signal priority from
`SIGNAL_PRIORITY_DEFAULT` (0) to `SIGNAL_PRIORITY_HIGH` (-100) on the
`"command names"` signal, so the fe-common handler runs before the IRC-core
`cmd_names` handler (`src/irc/core/irc-commands.c`), which is bound at default
priority.

The body of `cmd_names` in fe-channels.c is unchanged. It already:
- displays the cached nicklist for each locally-known channel and calls
  `signal_stop()` (which breaks the emit loop, preventing the lower-priority
  IRC handler from running and sending a raw `NAMES` to the server);
- accumulates unknown channels and re-emits `"command names"` for just those,
  letting the IRC handler query the server only for channels not cached
  locally. The re-emit is guarded by
  `g_strcmp0(channel, unknowns->str) != 0`, so when every channel is unknown
  it does not re-emit, terminating the recursion.

That design only behaves correctly when the fe-common handler runs first.
Previously both handlers were at default priority, so dispatch order depended
on registration/load order (equal-priority hooks are inserted before existing
ones, i.e. last-registered runs first), which could let the IRC handler send a
raw `NAMES` to the server before fe-common could `signal_stop()`. This commit
makes the ordering deterministic.

## Files touched
- src/fe-common/core/fe-channels.c

## Release-safety findings
None — safe to release.

The change is purely a signal-handler priority adjustment. `signal_stop()`
correctly halts the lower-priority handler (the emit loop in
`signal_emit_real` breaks on stop). `command_unbind` in `fe_channels_deinit`
matches by function pointer / user_data, not priority, so deinit still removes
the hook cleanly — no leak or dangling handler. No new input parsing or server
output is introduced, so there is no injection or memory-safety concern. Only
the two `cmd_names` handlers bind to this command, so there is no other
consumer whose ordering could be disturbed.

## Interactions with related changes
None. The IRC-core `cmd_names` handler is untouched and remains at default
priority; it still receives the re-emitted signal for unknown channels.

## NEWS accuracy
Accurate. The NEWS line "Fix /names sending a raw server event by binding it
first" precisely matches the change: the fe-common handler is bound first so
it can stop the signal before the IRC handler sends the raw NAMES server
command for locally-known channels.
