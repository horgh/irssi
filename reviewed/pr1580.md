# #1580 — Use the GIO resolver for name resolution and rename the resolve_prefer_ipv6 setting to irssiproxy_prefer_ipv6

- Commit: 62031f5b
- Verdict: NEEDS_ATTENTION

## What it changes
Replaces irssi's fork()-based blocking-resolver-in-a-child-process name
resolution with GLib's GResolver (GIO). Specifically:

- `net_gethostbyname()`/`net_gethostbyaddr()`/`net_gethosterror()`/
  `net_hosterror_notfound()`/`net_ip_compare()`/`ip4_any` are removed from the
  public `network.h` API. `net_gethostbyname()` becomes a `static` helper that
  wraps `g_resolver_lookup_by_name_with_flags()` and returns a new
  ref-counted `RESOLVED_IP_REC` (now holding a `GList<GInetAddress>` and a
  `GError`).
- A new `net_gethostbyname_first_ips()` does synchronous resolution for the
  blocking call sites (chat-commands host option, servers-setup source host,
  irssiproxy bind).
- The non-blocking path (`net-nonblock.c`) is rewritten: instead of forking a
  child and returning a pid + pipe, it issues
  `g_resolver_lookup_by_name_with_flags_async()` and returns a
  `GCancellable`; a continuation callback delivers the result.
- Server connect machinery is reworked: `SERVER_REC` swaps
  `connect_pipe[2]`/`connect_pid` for `connect_cancellable`;
  `SERVER_CONNECT_REC` swaps `last_failed_family` for
  `last_connected`/`last_failed` plus a cached `resolved_host`. Address
  selection changes from "pick a random A and random AAAA, prefer per
  `resolve_prefer_ipv6`" to "walk the resolver-ordered list, remember the last
  attempted index, and try the next entry on failure (re-resolving once the
  list is exhausted)".
- The `resolve_prefer_ipv6` setting is deleted from server core; a new
  `irssiproxy_prefer_ipv6` setting is added for the irssiproxy bind path only.
- ABI version bumped 56 -> 57. Bundled GLib bumped 2.74.3 -> 2.74.7; gobject
  and gio added as dependencies (incl. internal-static libffi/libgio/libgobject
  build wiring). Default `glib_log_domains` changed `all` -> `all -glib-gio:debug`
  and `glib_domain_wanted()` extended to match `domain:level` patterns.

Note: several defects in this commit were repaired by sibling follow-ups that
also ship in master (51322d6a restore ip4_any; e9281b2f older-GResolver compat;
88afc78a "GResolver fixes" — fixed a list-walk bug, the capsicum call in
network.c, an `ip` leak and a cancellable leak). The findings below are the
problems that remain at master HEAD.

## Release-safety findings

1. Use-after-free of `SERVER_REC` when a pending DNS lookup is cancelled
   (still present at master HEAD).
   The async resolve holds the raw `server` pointer (as `cont_data`) but takes
   no reference on it. The only `server_ref` is the initial one in
   `server_connect_init`. When a lookup is cancelled — `server_connect_failed()`
   (src/core/servers.c:54-64), `server_disconnect()` while
   `connect_cancellable != NULL` (servers.c:506-509), or the connect/reconnect
   timeout in servers-reconnect.c:123-130 — the code does
   `g_cancellable_cancel()` + `g_object_unref(cancellable)` and then
   `server_unref(server)`. Because the server is only in `lookup_servers` (not
   `servers`), `server_unref()` drops the last ref and `g_free()`s the server.
   GLib's GResolver still invokes the async callback afterwards (cancellation
   makes the op finish with `G_IO_ERROR_CANCELLED`; the GAsyncReadyCallback is
   still dispatched on a later main-loop iteration, and the threaded resolver
   may not return until `getaddrinfo` unblocks). `net_gethostbyname_callback`
   (net-nonblock.c) has no cancellation guard and unconditionally calls
   `data->cont(iprec, data->cont_data)` -> `server_connect_callback_resolved(
   iprec, <freed server>)`, which immediately dereferences the freed server
   (`server->connect_cancellable`, `server->connrec`, ...). This is reachable
   by /disconnect or a connect timeout while a name lookup is still in flight
   (slow/hanging DNS), i.e. realistic on flaky networks. The previous fork-based
   design avoided this because it removed the GIOChannel input source
   synchronously (`g_source_remove(connect_tag)`) so no callback fired after
   teardown. Needs a ref held across the async op (and released in the
   continuation) or an explicit cancellation check in the callback.

2. FreeBSD/Capsicum build break (still present at master HEAD).
   `net_gethostbyname()` is now `static` in network.c and has the new signature
   `(const char *addr, GResolverNameLookupFlags flags)`. The Capsicum symbiont
   still calls the old 3-arg form: `net_gethostbyname(addr, &ip4, &ip6)` at
   src/core/capsicum.c:282 (`symbiont_gethostbyname`). capsicum.c includes
   network.h, which no longer declares the symbol, and the definition is static
   anyway — so this fails to compile/link on builds with `have_capsicum`
   (FreeBSD). capsicum.c is only compiled when Capsicum is enabled
   (src/core/meson.build:3-6), so default builds are unaffected, but the
   Capsicum path of this feature was evidently not built/tested. This breaks an
   officially-supported build configuration.

Both items above are important for release safety. The siblings already in
master fixed the other defects this commit introduced (list-walk off-by-one /
NULL deref, `ip4_any` removal breaking DCC, missing old-GLib compat, the heap
`ip` leak and cancellable leak).

Behavior changes worth flagging (not blockers, but user-visible):
- Server IP selection is no longer randomized per attempt; it now follows the
  resolver's address order with sequential failover. Combined with caching
  `resolved_host` across reconnects, irssi will keep using the cached address
  list until every entry has failed before re-resolving — different from the
  old "re-resolve every connect" behavior; can matter for DNS-based failover/
  round-robin.
- `resolve_prefer_ipv6` is removed for server connections (IPv4-vs-IPv6
  preference is now whatever order GResolver returns). Users who relied on
  `/SET resolve_prefer_ipv6` for normal server connections silently lose it.

## Interactions with related changes
This change is the core of the "resolver" group. Sibling commits in master are
direct fix-ups layered on top of it and are required for it to build/run
correctly: 51322d6a (restore `ip4_any`, otherwise the IRC/DCC module fails to
link), e9281b2f (older-GResolver `< 2.59` compatibility shims in net-nonblock.c
and network.c), and 88afc78a (fixes the `net_gethostbyname_first_ips` list walk,
the network.c capsicum call signature, an `ip` leak, and a cancellable leak).
The two findings above survive all of these. There is a clear ordering
dependency: 62031f5b must not ship without 51322d6a/e9281b2f/88afc78a, and even
with them the capsicum.c:282 call and the cancellation UAF remain open.

## NEWS accuracy
Substantially accurate but understated. "Use the GIO resolver for name
resolution" is correct. "Rename the resolve_prefer_ipv6 setting to
irssiproxy_prefer_ipv6" is imprecise: for server connections the setting is
removed (no replacement), and a new, proxy-only `irssiproxy_prefer_ipv6` is
added — it is not a rename across the same scope. The NEWS line also omits
material scope: the ABI bump (56->57), the bundled GLib bump to 2.74.7 with new
gobject/gio dependencies, the change in default `glib_log_domains`, and the
shift from randomized to ordered/failover server-address selection.
