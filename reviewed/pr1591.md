# #1591 — Fix nickname truncation in netsplit messages to avoid a trailing comma-space

- Commit: 89dc74cb
- Verdict: SAFE

## What it changes
In `get_server_splits()` (src/fe-common/irc/fe-netsplit.c), the recorded
`maxnickpos` is changed from `chanrec->nicks->len` to
`chanrec->nicks->len - 2`. `maxnickpos` marks where the nick list is later
truncated when there are more split nicks than `netsplit_max_nicks`. Each nick
is appended as `"%s, "` (nick + comma + space), so the old position landed
just after the trailing ", " of the Nth nick, producing
`"nickN,  (+M more...)"`. Subtracting 2 moves the cut to just after the nick
itself, yielding `"nickN (+M more...)"`. Purely the truncation offset; one
line, no logic/control-flow change.

## Files touched
- src/fe-common/irc/fe-netsplit.c

## Release-safety findings
None — safe to release.

Bounds reasoning checked:
- `maxnickpos` is only *used* (line 181) when `netsplit_max_nicks > 0`
  (guarded at line 179). It is *set* (line 140) when
  `nick_count == netsplit_max_nicks`. So at the moment it is set, at least one
  `"%s, "` (>= 3 chars) has been appended, making `nicks->len >= 3` and
  `len - 2 >= 1`. No underflow despite `len` being unsigned; the stored int is
  non-negative.
- `read_settings()` clamps `netsplit_max_nicks <= netsplit_nicks_hide_threshold`,
  so the assignment at line 140 is always reached within the threshold guard
  block; the change does not create any uninitialized/stale `maxnickpos`.
- At truncation time (line 181) the string is first truncated by 2 (line 177);
  `maxnickpos` was captured at an earlier, smaller length, so it is always
  within bounds. `g_string_truncate` is also a no-op if the position exceeds
  the length, so it is safe in all cases.

No memory, UB, injection, ABI, build/portability, or default-behavior
concerns. The struct layout and settings defaults are unchanged.
